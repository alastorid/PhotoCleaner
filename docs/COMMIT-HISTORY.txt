Show Similar Photos: a doorway into the group browser

Right-click any photo — score grid, All Photos, a group cell, the lightbox —
and choose "Show Similar Photos" to open the Similar Group that photo belongs
to. The gate is GET /api/photo/{id}/similar, answering
{groupId?, totalCount, analyzed} from cached group membership.

It is a *show*, not a find. Grouping already happened when the FeaturePrints
were analysed and the answer is sitting in similar_group_members, so the whole
action is two indexed reads and a navigation: no image decoded, no FeaturePrint
generated, no pair compared, no Vision request, no grouping pass started. There
is one grouping implementation and one group browser; this is a second doorway
into them, not a second algorithm.

Three things the shape of the answer is doing work on:

- It reads *membership*, not the group list. A list is a presentation with
  rules of its own and may omit groups with nothing worth cleaning up, while
  "which group is this photo in" is a property of the photo. Keeping them
  apart is what lets a group of three with two protected favourites open from
  any of its three members, all three intact.
- `analyzed` is reported even when groupId is absent. "No similar photos" and
  "analysis has not reached this photo" are both an absent group and they are
  opposite facts; without the flag the UI would claim a photo is unique when
  nothing has compared it to anything yet.
- The item is never disabled. Both answers open the same view and say which of
  the two they are, which is more use than a greyed-out entry.

The Similar Groups view gains a second mode, distinguished by
state.groups.focused: the list of every group, or the one group a photo belongs
to. Same header, same sort control, same buildGroup — the list taken away, not
a second browser. Back returns to whichever view was underneath
(grid/allPhotos/groups) rather than always to the grid; All Photos is hidden
rather than torn down, so Back unhides the window instead of re-fetching around
the same anchor.

The originating photo is marked with .group-cell.origin and scrolled into view,
and stays where the sort put it — a marker that reordered the strip would be
making the ranking a lie. It is not a selection: .tile.selected remains the only
"queued for deletion" mark and nothing in this path touches it.

Also, on the group list itself:

- Frames are 128 px with a 1 px margin and no gap, so the strip reads as one
  contact sheet rather than a shelf of cards. The per-frame aesthetics score is
  gone — within a group the frames are near-identical, and a number under each
  one invites sorting by exactly the impression the strip exists to support. It
  stays in the tooltip and the lightbox.
- Paging is Previous/Next with the position stated, replacing a "Load more" that
  could only go forwards. A sentinel-driven list left the group you had just
  examined unreachable without reopening the view, and changed the page
  underneath the reader rather than at their request. No end marker: at either
  end the button that cannot go further is simply off.

Verified: 6 new assertions in a "similar photo lookup" suite, both halves of the
contract proven load-bearing by mutation (groupID -> nil fails 2 cases;
hasFeaturePrint -> always true fails 1). Clean build under -warnings-as-errors;
smoke 50/0/1. Against the real library the two empty paths answer
{"analyzed":true,"totalCount":0} and {"analyzed":false,"totalCount":0}, and an
unknown asset is a 404.

commit 693b33c74a6a5ec0f676542d297250c3a4fb0a3c
Author: alastorid <alastorid@gmail.com>

Fix three defects found reviewing the current tree

Two are mine, one is a security hole that predates this work.

1. The two analysis controls were not same-origin gated. Every other mutating
   route opens with crossOriginRefusal; POST /api/analysis/retry and
   POST /api/library/rescan did not. A bodyless POST is a CORS-simple request,
   so any page the user happened to be visiting could deliver one without a
   preflight. They are also the two most expensive routes in the app: retry
   requeues every failed asset and restarts the run, and rescan cancels an
   in-flight scan and starts a whole-library walk whose finishScan deletes every
   cache row the new scan does not stamp. Verified live: both now answer 403
   cross-site and still work same-origin.

2. `closeGroups` meant two different things to two callers. It is Back, and
   Back from a focused group returns to the group list it was opened from —
   correct for the Back button, and wrong for `openAllPhotos`, which replaces
   the view rather than unwinding it. Unwound there, it left the group view
   active and on screen underneath the window being opened, with both
   `state.groups.active` and `state.all.active` true at once. It now takes an
   explicit `leave` flag, so the two callers say which they mean.

3. `CacheStore.page` had three process-abort traps on `limit`. Writing the
   regression case turned up the third: `Int32(fetchLimit)` traps for anything
   outside Int32, and SQLite's LIMIT is an int32, so an unbounded Int is
   unrepresentable at the bind. The other two are `limit + 1` overflowing at
   Int.max, and the lookahead `removeLast()` running whenever
   `rows.count > limit` — true for any negative limit, since the query returns
   nothing and `0 > -1`. All three abort the process rather than throwing.
   Clamped once at the top against a stated ceiling, above the largest page the
   UI asks for, so no real request changes. Reverting the clamp makes the new
   case trap exactly as production does, so it is load-bearing.

Both new cases are pinned and mutation-checked: the same-origin one fails
without the gates, the limit one traps without the clamp. 212 assertions pass;
clean build under -warnings-as-errors; smoke 50/0/1.

Group view: continuous scrolling, denser frames, honest loading

Four changes to the Similar Groups browser, one of which was a bug.

1. The empty state claimed "No similar groups found" while a grouping pass was
   still running. Verified against this library: /api/groups reports
   building:true, total:0, featurePrints:37384 — so the view rendered "No similar
   groups found" over a library of 37,384 photos that simply had not been compared
   yet. That is a false negative for every photo in it, and it is the kind that
   convinces a user their library holds no duplicates. The empty state now
   distinguishes three facts — still grouping / no vectors read yet / genuinely no
   groups — and never prints a conclusion while the answer is being computed.

2. The list is now continuously scrollable in *both* directions, replacing the
   Previous/Next pager. A pager is a workaround for a one-way list; two sentinels
   bracketing the list are the actual fix, and they remove the buttons entirely.
   The window is startOffset/endOffset rather than one offset, so a pull at either
   end grows what is loaded instead of replacing it, and scrolling back is instant
   rather than another fetch. Prepending is the hard part and is handled: the
   document grows above the viewport, so the height delta is added back to the
   scroll offset afterwards or the reader is thrown backwards by exactly the height
   that was added. Overlap is trimmed by group identity, not by arithmetic, because
   a rebuild between two fetches shifts every offset by a different amount.

3. Frames fill the cell. The rank number and the meta line moved from grid rows
   and columns to overlays on the photo, which is what let the cell drop its padding
   and the strip drop its gap entirely — so the only separation between two frames is
   the 1px margin, and the strip is as wide as the photos in it rather than the
   photos plus chrome. 132px squares.

4. Loading is now visible and says what it is. One message for both ends and for
   the first load, with a spinner for a fetch and a slow, non-rotating variant for a
   grouping pass — a spinning wheel for several minutes reads as a hang. Poll during
   a pass no longer pages the list: the groups on screen are mid-replacement, so
   fetchGroupsStatus re-reads the status alone and leaves the window alone.

SetGroupOrder, rebuild and a finished pass all reset the window deliberately. The
groups already loaded were fetched under the old order or belong to a list that no
longer exists, so the sentinels would otherwise page through offsets that no longer
mean what they meant.

Verified: window arithmetic checked against a modelled server for downward scroll,
top prepend, repeated top pulls and a short library (contiguous, ordered, no
duplicates, no runaway growth); empty-state and busy-message selection checked for
the running / finished / first-load / focused-note cases; the live response above.
212 assertions pass, clean build, smoke 50/0/1.

Repaint only what a favourite change touches

Favouriting a photo called refreshAllTiles(), which walks every tile in the score
grid and the All Photos window and every cell of every open group, and
decorateTile rebuilds each one's flag chips and its whole accessible name. That
is the right tool for a change that can touch anything — a selection toggle, a
filter reset, a staged deletion — and the wrong one for a flag on a handful of
photos: on a grid holding thousands of loaded tiles, favouriting one photo
repainted the whole interface to change one star. It is not free either, since
holder.replaceChildren() per tile is a layout invalidation per tile.

refreshTilesById now looks up only the affected tiles, by their own data-id rather
than by position — an index-based repaint would restyle the wrong photo after the
All Photos window prepends a page and renumbers everything below it. Everything
that reads the flag lives inside decorateTile, so this only decides *which* tiles
ask it to redraw and there is still one place that knows what a favourite looks
like.

The group cells get the same treatment, and the per-cell decision is now a single
paintGroupCell shared with refreshGroups rather than a copy of it, so the targeted
and whole-list paths cannot disagree about the star or the staged mark. The
protection guard is preserved exactly as it was: the star there follows the
*protection* setting, not merely the Photos flag, which is deliberately different
from the grid tile where the favourite star shows regardless.

Also fixes a staleness the targeted repaint made visible. The lightbox prints the
flag on its own button — "★ Favourite — protected" versus "☆ Make favourite" —
and favouriting from there left it reading the old state until the photo was
naviged away from, which reads as the click having failed. It is repainted now,
and only when the photo on screen is one of the ones that changed.

The selection bar is still refreshed, because its protected-favourite count does
depend on this flag; it is one element, not a grid.

Verified: targeting checked against a modelled two-grid DOM for the single-id,
multi-id, post-prepend, unknown-id and 2000-tile cases (1 repaint, not 2000);
live round-trip through /api/favorites both ways, library left at its original 107
favourites. 212 assertions pass, clean build, smoke 50/0/1.

Release: versioned, tag-driven DMG publishing

Written by a parallel agent on the branch; committed here after verifying it.

The version stops being a constant. build.sh stamps CFBundleShortVersionString and
CFBundleVersion from PHOTOCLEANER_VERSION, and AppPaths.version reads them back out
of the running bundle for `--version`. One build writes the number and one place
reads it, so there is no second copy to forget to bump and no way for `--version` to
disagree with the artifact actually shipped. The regression suite compiles these
sources into a throwaway executable with no Info.plist of its own, which is the one
case that falls back to "dev" — a released app always runs inside its bundle.

PHOTOCLEANER_ARCH pins the architecture, validated rather than interpolated into a
target triple, so the published DMG cannot inherit whatever the runner happened to
be. Both values are refused on anything malformed before the compiler runs, and the
stamped version is read back afterwards — a bundle whose Info.plist disagrees with
the release being cut is exactly the kind of thing a user finds months later.

make-dmg.sh is hdiutil and nothing else. It packages the app with a symlink to
/Applications, then mounts the finished image and checks the bytes that ship: the
app, the executable, that the drag target really is a symlink to /Applications
rather than a copy (a folder there installs into the disk image and vanishes on
eject), the bundle identifier, and that the signature survives the round trip —
which is the check that would catch a bundle that verifies here but not after
hdiutil. It refuses to package an app whose stamped version or architecture is not
the one asked for.

Pushing a vN.N.N tag runs the same build, tests and smoke test as CI before
packaging, so a tag is not a licence to ship something that does not pass. Nothing
else publishes: main is still CI-only. Concurrency is per-tag with
cancel-in-progress false, so two tags in quick succession queue rather than the
second truncating the first's upload. The changelog is generated from commits since
the previous tag, guarded for the empty-array case that is the first release's job
failing on bash 3.2.

Verified locally: version stamping through to `--version` (1.2.3), and refusal of
a pre-release version and a bad architecture, both exiting 1. make-dmg.sh built a
real 2.1 MB DMG and passed all five mount-time checks; it correctly refused to
package the 1.2.3 app as 9.9.9 or as 1.2. Local build restored to 1.0.0. 212
assertions pass, smoke 50/0/1.

One asymmetry worth knowing: build.sh accepts N, N.N or N.N.N for local work, while
the workflow only publishes vN.N.N. That is intentional and documented, not a
mismatch to fix.

Delete flow: no panel, Shift to commit, staged photos leave the screen

The delete list had grown into a panel of its own — a summary line, a chip per
staged entry with its own ✕, a Review button, a Clear button and a Commit button
— for something that is two gestures. That is a lot of interface standing between
a decision and its only irreversible half.

It is now one control with two meanings. The button reads "Delete…" until something
is staged, "Commit delete N photos" once there is something to commit, and holding
Shift turns it into Commit at any time, so shift+click is the only gesture in the
app that calls /api/delete. The count on the button is the server's resolved count,
not a number that lives somewhere else and can drift from what will be destroyed.

Two things go with the panel, and both are losses worth naming. The warnings about
what will *not* be deleted — protected favourites kept, identifiers PhotoCleaner no
longer knows, a filter matching more than one deletion can name — were on that
panel, and there is nowhere else for them now. The Review button, which walked
every staged photo before committing, is gone. The refusal to commit while an entry
cannot be resolved is kept: that is a property of the deletion, not of the panel.

Staged photos now leave the screen. A photo queued for deletion has no tile, no
cell in a group strip, and no place in All Photos — it has already begun the journey
out of the library, and leaving it on screen with a mark on it says there is still a
decision to make about it. That removes the gesture that used to undo a mistake,
so ⌘Z is the way back: a stack of the last fifty changes to the list, each with its
direction recorded, so undoing a stage removes and undoing an un-stage restores.
⌥⌫ empties the whole list in one step, which is what a staged *filter* needs — it
is the one entry no photo click can take back.

Commit fires every staged entry's request together instead of one after another.
They cannot be merged into one request: each carries its own confirmToken, the
fingerprint of that entry's set as it resolved when it was staged, and a merged
request would need a fingerprint of the union that nobody ever previewed. So it is
N requests issued at once — one round trip's latency rather than N — with results
collected by index, because concurrent requests finish in whatever order the
network picks and a failure list that reordered itself would read as though two
commits of the same set deleted different photos.

Space now previews, and Space again quits, on tiles and on group cells. It used to
toggle the selection, which made the one key that "does something to this photo"
the one key that did not show you the photo. Enter keeps its meaning.

The group view joins the grid's pointer model: one click selects, Shift-click takes
the range from the last cell clicked, double click previews, Space toggles the
preview. Strips anchor their ranges separately from the grid, so a range in one
group is not measured from a cell last clicked in another. Ranges skip staged
photos, whose ranks stay put while their cells are gone. The preview's own
navigation skips them too, in the direction of travel, so ← steps back over what
was just staged rather than landing on it.

All Photos no longer assumes its document order is its array order: a prepend
restamps by the shift rather than by position, because restamping by position is
only correct while the DOM holds every row in the window, and it no longer does.
A tile repainted from its neighbour's row is a wrong star on a real photo.

Verification: tools/web-ui-tests.mjs drives the real index.html and app.js in jsdom
against a running PhotoCleaner and asserts on the DOM the app builds for itself —
22 checks over the delete flow, the Shift arming, the preview toggle, staging from
inside the preview, and the group pointer model. Each part was confirmed
load-bearing by mutation: removing the render-time filter, the undo direction, the
group reconciliation guard, the group anchor, or the space handler each fails the
check that covers it. Two defects it caught that reading would not have: an early
return in applyStagingToGrids that left the group strips unreconciled while the
grid was fine, and two references to names that were not in scope after splitting
buildGroupCell out of buildGroup.

Drop the utility-image filter entirely

The utility-image distinction — Vision's classification of screenshots, receipts
and documents — is gone from every layer: the `UtilityFilter` enum, the `?utility=`
query parameter, the filter predicate, the tile's "Aa" flag, the lightbox row, the
control-panel select, the `utility` field on `PhotoRow` and on a group's members,
and the count in the status payload.

Nothing visible changes for anyone who never touched the control, and that is the
point of how it was built: the default was `.include`, which emitted no predicate at
all, so every query this change touches already returned utility images. What is
removed is the ability to narrow by it, not a set of photos that were being hidden.

The stored column stays. `assets.is_utility` is in databases already on disk, and
`migrate()` is additive by rule — it creates with `IF NOT EXISTS` and never alters
an existing table — so an existing cache keeps a column nothing reads while a fresh
one never grows it. The upsert no longer assigns it, which on an old database means
the value simply goes stale; there is no migration to null it out, because there is
nothing to gain by writing to a column that is never selected from.

The `?utility=` parameter is now ignored rather than refused, and that is a
behaviour worth pinning rather than leaving to chance: a client predating this
removal still sends it, and it must neither fail the request nor narrow the
selection. Two tests assert exactly that — one over `/api/selection/preview`, one
over the All Photos window, the latter keeping `utility` in its hostile parameter
set for the same reason. Ignoring an unknown parameter is what the timeline
already relied on to be unfilterable.

The three tests that existed for this feature were rewritten rather than deleted,
because each was asserting something that still matters. "An out-of-enum value must
not fall back to the default" becomes "a stale parameter must not narrow or fail".
"Every in-enum value is accepted" loses a loop. "matching honours favorites:only"
loses its utility half and gains an `exclude` case, which it never checked and which
is the branch that actually protects nothing.

One assertion had to be corrected rather than carried over. `optional fields are
omitted, never sent as null` used `utility` as its optional field, because it was
the only one left once `date` had been covered above it. With nothing optional but
the date, that case now asserts the shape of an unanalysed row instead — same keys
as a scored one, no explicit nulls, and `score` sent as the number `0` that
`PhotoRow.score`'s non-optionality makes it, rather than absent. The old test would
have claimed an unanalysed row omits its score, which it never did.

Verified against the real library: `/api/status` reports `library` without the
utility count, rows and the filter echo are one key smaller each, and a stale
`?utility=only` returns 200 with byte-identical rows. 247 tests pass; the 22 web
checks pass against a cold server.

where this photo goes next, what it is, and what should happen to it, and that is
what the menu now offers.

becoming long enough that the word people scan for had moved to the far end of it,

read.

leave three fields that are written and never read — which is the kind of thing the

exists; it now names ⌘Z and ⌥⌫. The README's delete-list section still described
that panel — its chips, its ✕, its Review button, and the per-category scope
warnings that went with it — so it is rewritten around the Shift-click commit, and
it now says plainly that the scope is no longer broken down before you commit.

Verified against the real library: a favourite tile offers only "Remove from
Favourites", a plain one only "Favourite", neither ever disabled; clicking the item
writes the favourite and the label follows on reopen; "Remove from delete list" is

Self-update: check for a release, and install it in place

The app could only be updated by hand — download a DMG, quit, replace the
bundle. Nothing told the user a newer version existed, so a fix that shipped
reached nobody who was not already watching the releases page.

Five new types under Sources/PhotoCleaner/Update/, and one control:

- `UpdateVersion` parses and compares the app's own version, so "is this
  newer" is a comparison of versions rather than of strings. Components are
  zero-padded at construction so `1.2` and `1.2.0` are equal as well as
  unordered, which keeps `==`, `hash` and `<` telling the same story.
- `GitHubRelease` reads the releases feed. Only three of its fields are read —
  the tag, and the asset's name and download URL — because the endpoint is
  unauthenticated and its body is writable by anyone who can open a pull
  request. The asset whose name matches the tag exactly is the one installed;
  a release carrying an asset for the other architecture is refused by name
  rather than half-matched. The download URL is checked for `https`, and that
  is the whole of the check: the host is *not* pinned, because GitHub serves
  assets from objects.githubusercontent.com, so an allowlist would have to be
  a list of hosts rather than one.
- `Updater` is the state machine. Busy phases refuse a second run, a download
  that has no total reports no fraction rather than a false 100%, and a
  fraction is clamped to 0…1.
- `UpdateTarget` decides where an update may be installed, before anything is
  downloaded — so finding out after 15 MB that the app is running from a
  mounted image is not a thing that can happen. It refuses a bundle that is
  not a `.app`, a path under `/Volumes` even when the volume claims to be
  writable, and an unwritable parent, naming the reason in each case.
- `UpdateInstaller` mounts the image, verifies the version inside it against
  the tag, stages it with `ditto` (which preserves the signature; a plain
  copy does not), and swaps it in two moves so that a failure at any point
  leaves the previous app in place and launchable. A bad staged copy is
  detected after the swap and rolled back — `moveItem` succeeds on any
  directory, so the swap alone would report success for something unusable.
- `UpdateIndicator` draws the control in the title bar in every phase: a grey
  download glyph, an accent-coloured one when an update is waiting, and a
  blue arc sweeping 0→2π over a grey glyph while one downloads. Its tooltip
  says what a click will do rather than what the phase is.

The check runs at most once a day, deferred past launch, and is **on** by
default, with a menu item to turn it off. Deferring it matters: a network
round trip during startup is a delay the user pays before they can do
anything, so it happens once the window is up.

Settings gained the launch-check flag, defaulting to on. Absent fields decode
as their default, which needed a hand-written `init(from:)`: a synthesized
`Decodable` demands every key and does not fall back to a property's default,
so every `settings.json` written before a field existed failed to decode and
was silently replaced by all defaults. Adding a preference had been quietly
resetting every preference. The updater's scratch directory — the downloaded
image, the staged copy and the outgoing bundle — lives under Application
Support, not beside the app, so "writes nothing outside Application Support
and Logs" stays true.

selection, install-target refusals, phase fractions, indicator tooltips, and
the settings round trip including the old-file decode.

Self-update: a repository with no release is not a failure

`/releases/latest` answers 404 when a repository has never published a release.
That is the normal state of a project built from source — and it is PhotoCleaner's
own state today, so the first thing anyone running this would have hit.

The check reported it as `malformedRelease("the feed answered HTTP 404")`, which
put a red glyph in the title bar permanently and, on a click, told the user
something had gone wrong when there is in fact nothing to install. Both are wrong
about the same fact: 404 is an answer, not a failure.

`UpdateCheck.outcome(statusCode:body:)` now classifies the reply, and the actor
acts on the classification. It is a separate function rather than an `if` inside
`check` so the rule can be tested without a network, which is the only way to pin
it at all.

Only 200 is a release document. The earlier draft accepted the whole 2xx range,
and a case written against that draft asserted a 304 was fine — which it is not: a
304 to a request that carried no validators means the document was not handed over,
and accepting it would pass an empty body to the decoder instead of naming the
status. 204 and 206 are excluded for the same reason. 403 and 429 stay errors
regardless: those are GitHub declining to answer, and reporting "you are up to
date" for a question that was never asked would be a lie.

Also tightens the scheme check, which now reads `statusCode == 200` rather than
`(200..<300).contains(...)`, and says why in the comment above it — the previous
wording invited the same misreading the test fell into.

No response is cacheable: no-store on JSON, and no shared session

`smoke-test.sh` holds the app to storing no HTTP response outside Application
Support, and it had started failing with exactly one entry in
~/Library/Caches: a cached `http://127.0.0.1:8765/api/status`.

There were two causes, and either alone would have been enough.

The response carried no `Cache-Control` at all. `HTTPResponse.json` and
`.error` set a content type and nothing else, so every JSON route — the
counters in `/api/status`, a page of photos — was free to be written to a
client's disk cache. `no-store` rather than `no-cache`, because `no-cache`
still permits the body to be *stored* and only obliges a revalidation; the
write this prevents still happens. The client's `cache: 'no-store'` fetch
option was working around the missing header rather than replacing it, and
only for the browser.

And the second-launch probe used `URLSession.shared`, whose disk cache is
what actually wrote the entry. It now runs on an ephemeral session with
`urlCache = nil` and `.reloadIgnoringLocalCacheData` — the same session shape
the updater already uses, and for the same stated reason.

The stale read was the worse of the two, and neither header nor session fixes
that on its own: a cached 200 for a port whose server has since quit would
report "PhotoCleaner is already running" and focus a window that is not there.

Verified against the built app rather than assumed. `/api/status` now answers
`Cache-Control: no-store`; with ~/Library/Caches cleared, a second launch on a
busy port still detects the running instance and leaves no cache directory
behind at all. The smoke test is 50 passed, 0 failed.

One test, "no JSON route may be cached", across five routes plus a 404 — a 404
body is as much a live answer as a 200. Checked that it fails without the
header: it reports `expected Optional("no-store"), got nil`, which is the exact
defect.
